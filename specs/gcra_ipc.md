# GCRA IPC Specification

Status: draft
Reference: gcra_ipc
Spec source of truth for: библиотека gcra_ipc — include/gcra_ipc/gcra_ipc.h, src/gcra_ipc.cpp

## Overview
Межпроцессный ограничитель темпа (GCRA — Generic Cell Rate Algorithm) в
разделяемой памяти: одно слово состояния, без таймеров, потоков, блокировок
и системных вызовов на горячем пути. Семантика — шейпер, не полисер:
списание квоты всегда успешно, метод `shaper::Reserve` возвращает
абсолютный deadline, до которого вызвавший обязан подождать, прежде чем
действовать; отказа не существует. Аналогия: виртуальная очередь, живущая в
одном `uint64_t`. Заявка несёт переменную стоимость в единицах (например,
байтах): темп хранится напрямую (`rate_per_second`, единиц/с), инкремент на
заявку — `ceil(units × 1e9 / rate_per_second)` с единственным округлением
вверх, погрешность меньше наносекунды при любой ставке — библиотека
пригодна как сетевой троттлер до `100 Гбит/с` и выше.
Tick-less: пересчёт ленивый, в момент вызова; фоновых потоков нет.
Часы читает вызывающий — сама библиотека на горячем пути времени не
спрашивает. Никто никого не будит: у каждого ждущего свой deadline,
«стада» нет по построению.

## Scope
In: публичный C++-API (`shaper::Open`, `shaper::Create`, `shaper::CreateOrThrow`, `shaper::Reconfigure`, `shaper::Reserve`); формулы GCRA с переменной стоимостью заявки; прямое хранение темпа и burst-окна и допустимые диапазоны rate/units/window; layout shm-объекта и политика версионирования; инициализация shm без блокировок; memory ordering атомиков; контракт абсолютного deadline; однопоточный golden-тест расчётов.
Out (non-goals): многопоточные и многопроцессные тесты; счётчики, статистика и метрики в shm; отмена резервирования и подрезка position; detach/unmap отображения; строгий FIFO слотов; семантика полисера (отклонение заявок); способ ожидания до выданного deadline — на вызывающем; конфиг-интеграция и разбор конфигурационных форматов — вне библиотеки.

## Definitions
- shaper — семантика шейпера: списание
  всегда успешно, темп поддерживается ожиданием вызывающего до deadline;
  отклонения заявок не существует.
- deadline — абсолютный момент времени
  в нс `CLOCK_MONOTONIC`, раньше которого вызывающий не совершает
  ограничиваемое действие.
- units — стоимость заявки в
  абстрактных единицах (например, байтах); заявка с `units == 0` — пустая.
- position — `position_ns`: единственный
  атомарный элемент состояния; виртуальная position расписания очереди, нс.
- slot — слот заявки: возвращаемый
  deadline, вычисляемый как `max(position − burst_window, now)` с защитой от
  underflow.
- rate-per-second — `rate_per_second`:
  хранимый темп, единиц/с; инкремент на единицу стоимости —
  `ceil(1e9 / rate_per_second)` нс; `0` — лимит выключен.
- burst-window — `burst_window_ns`:
  кредитное окно, нс: насколько слот может начинаться раньше position;
  конфигурируется явно и хранится как задано, включая `0` — строгий
  спейсер, burst отсутствует.
- burst-budget — мгновенный кредит в
  единицах стоимости: `B = floor(burst_window_ns × rate_per_second / 1e9)`;
  немедленный burst серии заявок после простоя — до `B + units` единиц.
- re-anchor — ре-анкор: отсчёт нового
  значения position от `max(position, now)`, а не от слота заявки.

## Interface
```cpp
// gcra_ipc.h
namespace gcra_ipc {

class shaper
{
public:
    // Открывает существующий shm-объект по имени; nullptr, если объекта нет
    // (R25) или magic чужой (R19).
    static std::shared_ptr<shaper> Open(const std::string& shmName);

    // Открывает существующий или создаёт новый shm-объект и конфигурирует
    // rate/burst-window; nullptr при ошибке создания/конфигурации (R15, R17-R19).
    static std::shared_ptr<shaper> Create(const std::string& shmName, std::uint64_t ratePerSecond, std::uint64_t burstWindowNs);

    // Как Create, но при ошибке бросает исключение gcra_ipc_error
    // с соответствующим кодом errno.
    static std::shared_ptr<shaper> CreateOrThrow(const std::string& shmName, std::uint64_t ratePerSecond, std::uint64_t burstWindowNs);

    // Переконфигурация rate/burst-window на лету: position не подрезается (R16);
    // некорректная конфигурация — исключение, параметры не меняются (R15).
    void Reconfigure(std::uint64_t ratePerSecond, std::uint64_t burstWindowNs);

    // Списание квоты: всегда успешно, возвращает абсолютный deadline (нс
    // CLOCK_MONOTONIC) — слот заявки, не новое position (R2).
    std::uint64_t Reserve(std::uint64_t nowNs, std::uint64_t units);

private:
    shaper() = default;
    ...
};

using shaper_ptr = std::shared_ptr<shaper>;

} // namespace gcra_ipc
```

Тип указателя: `shaper_ptr` — `std::shared_ptr<shaper>`:
сценарий — один шейпер на несколько потоков и компонентов процесса,
владение разделяемое; мотивация выбора и отвержение `std::unique_ptr` —
J24.

Горячий путь: `Reserve` определён inline в заголовке — напрямую или через
detail-inline-заголовок — над отображённым `gcra_ipc_state` и содержит одно
CAS (R11); фабрики `Open`/`Create`/`CreateOrThrow` и `Reconfigure` — не
горячий путь, системные вызовы встречаются только в них.

Layout shm-объекта — внутренние типы библиотеки (detail-inline-заголовок,
например `gcra_ipc_detail.h`), публичный заголовок их не экспортирует;
бинарный контракт межпроцессной совместимости:

```cpp
// gcra_ipc_detail.h (внутренние типы, layout-контракт)
struct alignas(64) gcra_ipc_state {
    std::atomic<uint64_t> position_ns;
    std::atomic<uint64_t> rate_per_second;
    std::atomic<uint64_t> burst_window_ns;
};

struct gcra_ipc_shm {
    std::atomic<uint32_t> magic;
    uint32_t version;
    alignas(64) gcra_ipc_state state;
};
```

Аргументный контракт:
- `Open`: `shmName` — непустая строка, имя POSIX shm-объекта с ведущим `/`;
  результат — `shaper_ptr` либо `nullptr`: объект отсутствует (R25),
  системная ошибка (R26), пустое имя или чужой magic (R19); при `nullptr`
  системный `errno` установлен.
- `Create`: `shmName` — как у `Open`; `ratePerSecond` — `uint64`, единиц/с,
  диапазон `0..UINT64_MAX`, хранится без преобразования (R13); `burstWindowNs` —
  `uint64` в нс, диапазон `0..UINT64_MAX`, хранится без преобразования,
  включая `0` — строгий спейсер; результат —
  `shaper_ptr` либо `nullptr` при системной ошибке (R17), чужом magic (R19)
  или некорректной конфигурации (R15); при `nullptr` системный `errno`
  установлен.
- `CreateOrThrow`: аргументы те же, что у `Create`; ошибки — исключение
  `gcra_ipc_error` с системным кодом либо кодом `EINVAL`
  (R15, R17, R19).
- `Reconfigure`: `ratePerSecond` и `burstWindowNs` — как у `Create`; результата нет;
  некорректная конфигурация — `gcra_ipc_error` (R15).
- `Reserve`: `nowNs` — текущее время `CLOCK_MONOTONIC` в нс; `units` — `uint64` в диапазоне `0..UNITS_MAX` по контракту использования — рекомендуемая рабочая граница, проверок в коде нет, контроль на вызывающем; жёсткая арифметическая граница — `UNITS_HARD_MAX`: при `units > UNITS_HARD_MAX` числитель инкремента R5 `units × 1e9` переполняет u64 (определённый wrap, не UB), метод и её не валидирует; результат — абсолютный deadline в нс; ошибок метод не возвращает.

## Configuration
| Name | Allowed values | Default | Effect |
|---|---|---|---|
| `ratePerSecond` (аргумент `Create`/`CreateOrThrow`/`Reconfigure`) | uint64, `0..UINT64_MAX` единиц/с | нет (обязателен) | Целевая скорость; хранится в shm без преобразования; `0` — лимит выключен, fail-open (R3) |
| `burstWindowNs` (аргумент `Create`/`CreateOrThrow`/`Reconfigure`) | uint64 `0..UINT64_MAX` нс | нет (обязателен) | Burst-окно в нс; хранится без преобразования (R13); `0` — строгий спейсер, burst отсутствует; burst-budget — `floor(burstWindowNs × ratePerSecond / 1e9)` единиц (R9) |
| `UNITS_HARD_MAX` | `fixed` `2^34` единиц | — | Жёсткая арифметическая граница контракта `units`: при `units > UNITS_HARD_MAX` числитель инкремента R5 `units × 1e9` переполняет u64 — определённый wrap, не UB; инкремент занижен относительно точного значения, слот (R4) и position (R6) занижены — иных последствий нет (J13); `Reserve` границу не проверяет — контроль на вызывающем |
| `UNITS_MAX` | `fixed` `2^24` единиц (`16` МиБ) | — | Рекомендуемая рабочая граница контракта `units` (Interface, Constraints) — практический предел размера сетевой заявки, рекомендация использования, а не жёсткая константа; запас до `UNITS_HARD_MAX` — `2^10` (J13); `Reserve` границу не проверяет — контроль на вызывающем |
| `GCRA_IPC_MAGIC` | `fixed` fourcc `"GCR1"` | — | Маркер инициализации shm-объекта (R18, R19); значение не зависит от смены фасада (R20, J20) |
| `GCRA_IPC_VERSION` | `fixed` `1` | — | Текущая версия layout в поле `version` (R20) |
| `state-line-alignment` | `magic` 64 байта (безымянный литерал `alignas(64)` в коде) | — | Выравнивание `gcra_ipc_state` на границу линии кэша: состояние — ровно одна линия (J17) |

## Behavior
- R1. `shaper::Reserve` всегда успешна и возвращает абсолютный deadline в нс `CLOCK_MONOTONIC`: вызвавший обязан не совершать ограничиваемое действие раньше этого момента; пути отказа не существует.
- R2. Возврат `Reserve` — слот, не новое значение position: абсолютный deadline, равный вычисленному слоту `max(position_ns − burst_window_ns, now_ns)` (R4), а не `new_position_ns` (R6); заявка с `units == 0` — no-op: возвращает `now_ns`, не обращаясь к атомикам состояния.
- R3. Лимит выключен (`rate_per_second == 0`): `Reserve` возвращает `now_ns`, не изменяя position (fail-open).
- R4. Слот заявки: `deadline = max(position_ns − burst_window_ns, now_ns)`; при `position_ns < burst_window_ns` (underflow вычитания) слот равен `now_ns`.
- R5. Инкремент position: `increment_ns = ceil(units × 1e9 / rate_per_second)`; это единственное округление на заявку, всегда вверх.
- R6. Новое значение position: `new_position_ns = max(position_ns, now_ns) + increment_ns` — ре-анкор от `max(position, now)`, а не от слота заявки.
- R7. При `units >= 1` и включённом лимите `increment_ns >= 1` нс, поэтому `new_position_ns > position_ns` строго: position монотонен, ABA исключён, слоты не повторяются.
- R8. Ре-анкор R6 не копит кредит за простой: после паузы любой длины немедленные слоты получает только серия заявок суммарной стоимостью в пределах burst-budget.
- R9. Серия заявок, приходящих одновременно после простоя, получает немедленные слоты, пока суммарная стоимость предшествующих заявок серии не превышает burst-budget `B = floor(burst_window_ns × rate_per_second / 1e9)`; немедленный burst серии в единицах стоимости — `B + units` последней немедленной заявки; следующая заявка серии ждёт `(суммарная стоимость − B) × 1e9 / ratePerSecond` нс; при единичной стоимости немедленных слотов ровно `B + 1`.
- R10. При стабильной в течение окна конфигурации и действии каждого вызвавшего не раньше его deadline суммарная стоимость заявок с deadline внутри окна длительностью `T` нс не превышает `T × ratePerSecond / 1e9 + B + UNITS_MAX`; при единичной стоимости — `T × ratePerSecond / 1e9 + B + 1` заявок.
- R11. Списание — один CAS над `position_ns` на попытку (compare_exchange: success `memory_order_acq_rel`, failure `memory_order_acquire`); проигравшая попытка перечитывает position и параметры и повторяет цикл; если при перечитывании `rate_per_second == 0`, цикл завершается возвратом `now_ns`.
- R12. Порядок слотов равен порядку побед CAS; строгого FIFO между потоками и процессами нет.
- R13. Конфигурирующая операция (`Reconfigure` либо конфигурирующая часть `Create`/`CreateOrThrow`) сохраняет `rate_per_second = ratePerSecond` и `burst_window_ns = burstWindowNs` без преобразования; при `ratePerSecond == 0` лимит выключен (R3) и значение окна на поведение не влияет; при `burstWindowNs == 0` — строгий спейсер: burst отсутствует, слот R4 равен `max(position_ns, now_ns)`.
- R14. Конфигурирующая операция публикует параметры атомарными store: сначала `burst_window_ns`, затем `rate_per_second` (release); повторные вызовы `Reconfigure` перезаписывают параметры.
- R15. Конфигурирующая операция отклоняет запрос без изменения параметров кодом `EINVAL` при нулевом указателе отображённого состояния — внутренняя защита от ошибки отображения; параметров, требующих отказа, больше нет: любые значения `ratePerSecond` и `burstWindowNs` валидны; `Reconfigure` и `CreateOrThrow` сигнализируют исключением `gcra_ipc_error` с кодом, `Create` — возвратом `nullptr` с установленным `errno`.
- R16. Смена rate или burst-окна на лету (`Reconfigure`, повторный вызов `Create`/`CreateOrThrow` на существующем объекте): position не подрезается и не пересчитывается; все ранее выданные абсолютные deadlines остаются валидными; новые заявки считают по новым значениям — и по новой ставке, и по новому окну: слоты R4 вычисляются по актуальной паре (`rate_per_second`, `burst_window_ns`).
- R17. `Create` и `CreateOrThrow` открывают существующий или создают новый shm-объект: `shm_open(shm_name, O_RDWR | O_CREAT, 0600)` → `ftruncate(fd, sizeof(gcra_ipc_shm))` → `mmap(NULL, sizeof(gcra_ipc_shm), PROT_READ | PROT_WRITE, MAP_SHARED | MAP_POPULATE, fd, 0)` → `close(fd)`; системные ошибки цепочки дают `nullptr` с системным `errno` у `Create` и исключение `gcra_ipc_error` с системным кодом у `CreateOrThrow`.
- R18. Инициализация без блокировок: создающий процесс (attach-or-create: `Create`/`CreateOrThrow`), увидевший `magic == 0` (свежий zero-filled shm), выполняет `atomic_store(GCRA_IPC_MAGIC, memory_order_release)`; записывающие видят одно и то же значение, поэтому гонка нескольких первых создателей безвредна; `Open` magic не публикует — без побочных эффектов по своей норме R25; нулевое состояние валидно и для `Open`: `position_ns == 0` — очередь пуста, параметры `0` — fail-open, поскольку эпоха tmpfs умирает вместе с машиной, как и эпоха `CLOCK_MONOTONIC`.
- R19. Существующий shm-объект с ненулевым `magic`, отличным от `GCRA_IPC_MAGIC`, отвергается всеми фабриками: `Open` и `Create` возвращают `nullptr` с `errno = EINVAL`, `CreateOrThrow` бросает `gcra_ipc_error` с кодом `EINVAL`.
- R20. Layout зафиксирован парой (`GCRA_IPC_MAGIC`, `version`): несовместимое изменение layout обязано использовать новое значение magic и новое имя shm-объекта — правило действует после первого выпуска, а дорелизная правка layout (хранение темпа напрямую вместо кодированного интервала) выполнена до выпуска при отсутствии релизованных объектов и ротации не потребовала (J20); языковой фасад библиотеки не входит в layout-контракт — смена фасада без изменения бинарного layout не требует нового magic и нового имени shm-объекта; поле `version` хранит `GCRA_IPC_VERSION` для диагностики и фабриками не проверяется.
- R21. Loads параметров `rate_per_second` и `burst_window_ns` — `memory_order_relaxed` (read-mostly); CAS position — `acq_rel`/`acquire` (R11); после проигранного CAS параметры перечитываются.
- R23. Счётчики, статистика и метрики в shm не ведутся: наблюдаемость вне скоупа библиотеки.
- R24. Crash-safety: `kill -9` любого процесса-участника не портит состояние и не требует восстановления; протокола очистки и восстановления нет.
- R25. `Open` открывает только существующий shm-объект: `shm_open(shm_name, O_RDWR, 0600)` без `O_CREAT` — отсутствующий объект даёт `nullptr` с `errno = ENOENT` и без побочных эффектов.
- R26. `Open` применяет к открытому объекту ту же цепочку `ftruncate` → `mmap` → `close(fd)`, что и `Create` (R17): `ftruncate` идемпотентен корректному объекту и достраивает объект, оставленный оборванным созданием; системные ошибки цепочки — `nullptr` с системным `errno`.

## Constraints
- Шейпер-контракт: инвариант R10 выполняется при условии, что вызвавшие действуют не раньше выданных deadline; нарушившие контракт вызвавшие не ограничиваются библиотекой.
- Возвращаемый `Reserve` deadline абсолютный, нс `CLOCK_MONOTONIC`; способ ожидания до него — активное ожидание, сон, событийный цикл — библиотекой не предоставляется и не предписывается.
- Контракт использования: `units <= UNITS_MAX` — рекомендуемая рабочая граница размера сетевой заявки; `Reserve` границу не проверяет — контроль на вызывающем.
- Жёсткая арифметическая граница: при `units > UNITS_HARD_MAX` числитель инкремента R5 `units × 1e9` переполняет u64 — определённый wrap, не UB; инкремент занижен относительно точного значения, слот (R4) и position (R6) занижены — последствий сверх занижения инкремента, слота и position нет (J13).
- Точность: пере-заряд на заявку меньше `1` нс при любой ставке (J5) — округление инкремента единственно и всегда вверх, погрешности кодирования темпа нет.
- Конкурентная смена конфигурации: возможны переходные попытки CAS со смешанной парой (старый темп, новое окно) или наоборот; каждая заявка использует одну согласованную внутри попытки пару; гарантия R10 применяется к стабильной конфигурации, переходный кредит ограничен `max(burst_window_old, burst_window_new) × max(rate_old, rate_new) / 1e9 + UNITS_MAX`.
- Брошенные слоты: процесс, умерший с зарезервированным position в будущем, не отменяет резервирование — виртуальная очередь разряжается темпом rate, механизма отмены нет.
- Отображение живёт до конца процесса: detach/unmap API отсутствует; имена shm-объектов при ротации layout лежат на политике владельца приложения.
- Очередь неявно неограничена: каждый дождётся слота; все времена — нс `CLOCK_MONOTONIC`, немонотонные часы недопустимы.

## Justification
- J5. Округление R5 — ceil: floor и round-to-nearest могут недобрать инкремент и разогнать фактическую скорость выше настроенной, ломая R10; ceil гарантирует инкремент не менее `1` нс при `units >= 1` (основа R7) и пере-заряд меньше `1` нс на заявку при любой ставке.
- J10. Эскиз доказательства R10: из R5–R6 position после заявки не меньше её deadline плюс стоимость × интервал, а из R4 deadline каждой следующей заявки не меньше position минус окно; суммируя по заявкам окна длительностью `T`, получаем суммарную стоимость не больше `(T + burst_window_ns) × ratePerSecond / 1e9 + стоимость последней заявки`, что раскрывается в R10.
- J13. Почему темп и burst-окно хранятся напрямую, без кодирования (R5, R13, R15): темп — без дробной шкалы интервала: точность лучше `1` нс на заявку при любой ставке; исчезает развилка точность/`UNITS_MAX` — шкала теряла точность на высоких ставках и переполняла u64 на низких: произведение границы заявок на кодированный интервал не помещалось в u64 уже при `10` ед/с, низкая ставка отвергалась как некодируемая; цена — целочисленное деление на горячем пути, `~20–40` тактов на попытку CAS: при `100 Гбит/с` = `1.25e10` ед/с и заявках размера MTU это `~8.3e6` резерваций/с, деградация различима лишь при `2–3e7` резерваций/с на ядро — запас `~3x`; окно — явно в нс, а не косвенным кодированием через число немедленных слотов единичной стоимости: явное окно прямее — пользователь выражает всплеск в абсолютном времени (например, `200 ms`) или в единицах стоимости через `window × rate / 1e9` (байты — окно, умноженное на байтовую ставку); косвенное кодирование привязывало окно к ставке — смена ставки молча меняла окно — и требовало верхней границы числа слотов со страховкой переполнения кодирования; `UNITS_MAX` — рекомендуемая рабочая граница размера сетевой заявки, не жёсткая константа, жёсткая арифметическая граница переполнения числителя `units × 1e9` — `UNITS_HARD_MAX`, запас между границами `2^10` (R5); возможная будущая оптимизация — precomputed reciprocal (умножение на заранее вычисленный обратный множитель вместо деления), ценой возврат ограничения переполнения на диапазон числителя — отвергнута как преждевременная.
- J16. Почему смена ставки R16 без подрезки position: подрезка нарушила бы глобальную монотонность position (R7) и обесценила бы уже выданные дальние deadlines; очередь при снижении ставки разряжается темпом старой ставки до исчерпания.
- J17. `alignas(64)` и одна линия кэша: состояние изменяется CAS с каждой заявкой; соседние поля или второй линии вызвали бы false sharing между процессами.
- J18. Magic публикуется первым release-store: zero-filled страница tmpfs — валидное «неинициализировано»; единственный атомик готовности — magic, отдельный флаг готовности не нужен.
- J20. Почему magic и имя shm-объекта сохранены (R20): дорелизная правка layout (хранение темпа напрямую вместо кодированного интервала) выполнена до первого выпуска библиотеки — релизованных объектов не существует, ротация magic и имени нужна только для совместимости с живыми объектами; межпроцессный контракт — только бинарный layout, языковой фасад в него не входит — смена фасада также не меняет layout, значения `GCRA_IPC_MAGIC` и `GCRA_IPC_VERSION` сохранены; правило ротации действует для пост-релизных изменений.
- J21. Loads параметров relaxed: параметры read-mostly, цена acquire на горячем пути не оправдана; согласованность пары параметров с position не нужна инвариантам — переходные смеси ограничены в Constraints.
- J22. Почему возврат `Reserve` — абсолютный deadline (R1, R2): остаток ожидания всегда вычисляется вычитанием текущего времени из deadline, поэтому прерывания и повторные входы в ожидание у вызывающего не накапливают дрейф; способ ожидания библиотека не навязывает — активное ожидание, сон или событийный цикл остаются на вызывающем (Constraints).
- J23. Без счётчиков (R23): любая статистика в shm — второй RMW и лишний bounce линии на каждой заявке; наблюдаемость возлагается на вызывающих.
- J24. Выбор `std::shared_ptr<shaper>`: сценарий — один шейпер на несколько потоков и компонентов процесса, владение разделяемое; `std::unique_ptr` отвергнут, потому что единственный владелец противоречит разделению и потребовал бы внешнего owner-объекта; объект хранит только указатель отображения, деструктор тривиален (отображение живёт до конца процесса), счётчик ссылок не задействован на горячем пути — `Reserve` вызывается через указатель без копий `shaper_ptr`.

## Error handling
- Код `EINVAL` — некорректные аргументы: пустое имя или чужой magic (R19), нулевое отображённое состояние у конфигурирующей операции (R15): разовая ошибка, вызывающий исправляет аргументы и повторяет; сигнал — `nullptr` с `errno = EINVAL` у `Open`/`Create`, исключение `gcra_ipc_error` у `CreateOrThrow`/`Reconfigure`.
- Системные ошибки `shm_open`/`ftruncate`/`mmap`: `Open` и `Create` возвращают `nullptr`, системный `errno` пробрасывается (R17, R26); `CreateOrThrow` бросает `gcra_ipc_error` с системным кодом.
- `ENOENT` у `Open` — отсутствие shm-объекта (R25): штатный отличимый случай, вызывающий решает создать объект фабрикой `Create`.
- `Reserve` ошибок не возвращает (R1).
